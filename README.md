# QR Air Transfer

Передача файлов «по воздуху» через поток динамически меняющихся QR-кодов —
без Wi-Fi, Bluetooth, интернета и сопряжения устройств. Отправитель показывает
на экране быстро сменяющиеся QR-коды, получатель снимает их камерой и собирает
файл по мере приёма.

Это PWA: работает в любом современном браузере (Android, iOS, ПК), после
первого открытия — полностью офлайн.

## Ключевые цифры

| | |
|---|---|
| Максимум в одном QR | **2953 Б** (версия 40, коррекция L), полезных в кадре — 2938 Б |
| Предел камеры 30 к/с + экран 60 Гц | ≈ 15.8 разных кодов/с → **≈ 43 КБ/с** для одного кода v40 |
| Предел камеры 60 к/с + экран 120 Гц | ≈ 31.6 кодов/с → **≈ 86 КБ/с** |
| Реально телефон → телефон с рук | 10–30 КБ/с |
| Сжатие | смешивание контекстов (PAQ-класс): на 20–51 % меньше deflate, лучше xz/bzip2; метод выбирается по полному времени передачи |
| Избыточность fountain-кода | +≈2 кадра на файл до 1024 блоков, 1–4 % для больших |
| Максимальный размер файла | 4 ГиБ по протоколу; практически — сотни МБ (память) и часы (время) |

Вывод формул и все таблицы — в [docs/THEORY.md](docs/THEORY.md); в приложении
есть интерактивный калькулятор и замер конкретного устройства (раздел «Лимиты»).

## Как пользоваться

1. **Отправитель**: «Отправить» → выбрать один или несколько файлов, папку
   (на компьютере) или вставить текст → «Начать передачу». Режим «⚡ Авто»
   сам подбирает параметры: v25-L, частоту смены кодов под измеренную частоту
   экрана (20 смен/с на 60 Гц — безопасно и для камер 30 к/с, и для 60 к/с),
   на широком экране ноутбука или планшета — 2 кода друг над другом (режим
   «2 кода» всегда ставит их вертикально: пара заполняет кадр телефона,
   который держат вертикально), и метод сжатия по полному времени передачи.
   Ручная настройка — в раскрывающемся блоке. Долгое сжатие можно отменить.
   Экран переходит в полноэкранный режим и не гаснет.
2. **Получатель**: «Получить» → «Включить камеру» (если доступ к камере уже
   разрешён, она включается сама) → навести на экран отправителя так, чтобы все
   коды целиком были в кадре и занимали бо́льшую его часть. Найденные коды
   подсвечиваются зелёным (красным — найден, но не прочитан), синие пунктирные
   рамки — коды, за которыми приёмник следит. Подсказки на экране скажут, если
   код у края кадра, слишком мелкий или отправитель меняет коды слишком часто.
3. Когда прогресс дойдёт до 100 %, данные распаковываются и проверяются по
   CRC-32. Файлы можно сохранить по одному, все сразу одним ZIP-архивом
   (собирается при нажатии), отправить через «Поделиться» или скопировать
   (для текста). Сохранённые кадры удаляются только после успешной
   распаковки: если вкладка упадёт на этом шаге, файлы распакуются снова при
   следующем открытии.

Начинать приём можно в любой момент и на нескольких устройствах сразу:
пропущенные кадры не нужны, подойдут любые следующие.

**Обрыв и продолжение.** Если вкладка получателя перезагрузилась (iPhone
выгружает её при нехватке памяти, блокировке экрана, переключении приложений),
принятое не пропадает: кадры сохраняются в IndexedDB, и при следующем открытии
«Получить» прогресс восстанавливается — достаточно снова включить камеру
(«Начать заново» удаляет сохранённое). ID передачи — хеш содержимого и
размера блока, поэтому перезапуск отправителя с тем же файлом и настройками
продолжает ту же передачу, причём с того кода, на котором он остановился.
Для этого отправитель запоминает, какой метод сжатия «Авто» выбрал для этого
содержимого: выбор зависит от замеренной скорости процессора, и без памяти
другой метод дал бы другой поток и другой ID.

Советы: яркость экрана на максимум, без бликов; телефон-получатель неподвижно
(подставка). Если «Распознаётся» меньше, чем «Камера» — не успевает процессор:
снизьте разрешение до 720p или включите «центр кадра».

**60 кадров в секунду.** Получатель по умолчанию просит у камеры 60 к/с (при
необходимости жертвуя разрешением); фактический режим написан в «Настройках
камеры». Найдя коды, приёмник следит за каждым отдельно (синие пунктирные
рамки): распознаёт только область вокруг кода, уменьшенную до ~3,5 пикселя на
модуль, — каждый код в своём потоке, и сам добавляет потоки (до 6), если
кадры теряются, — так телефон успевает обработать каждый кадр. Раз в 15
кадров весь кадр просматривается заново в поисках новых кодов. Отправителю при этом ставьте пресет «60 к/с» (20 смен кода в
секунду, по 3 кадра камеры на код). При 30 сменах/с камера и экран 60 Гц
«бьются»: приём периодически замирает на десятки секунд (см. docs/THEORY.md,
«Биения»), приёмник об этом предупреждает.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173 — камера работает на localhost
npm run build      # статическая сборка в dist/
npm test           # модульные и сквозные тесты (Vitest)
npm run test:e2e   # тесты в Chromium с фейковой камерой (Playwright)
```

Камера в браузере доступна только по **HTTPS** (или на `localhost`), поэтому
для телефонов приложение нужно разместить на HTTPS-хостинге. В репозитории
есть workflow `.github/workflows/pages.yml`: включите
*Settings → Pages → Source: GitHub Actions*, и каждый пуш в `main` будет
публиковать приложение на GitHub Pages. Подойдёт и любой статический хостинг —
все пути относительные.

### Если `npm install` падает с ошибкой сертификата

`UNABLE_TO_GET_ISSUER_CERT_LOCALLY` / `SELF_SIGNED_CERT_IN_CHAIN` означает, что
npm-репозиторий или прокси в корпоративной сети подписан сертификатом, которому
Node.js не доверяет. На macOS можно передать Node все сертификаты, которым
доверяет система:

```bash
security find-certificate -a -p \
  /System/Library/Keychains/SystemRootCertificates.keychain \
  /Library/Keychains/System.keychain \
  ~/Library/Keychains/login.keychain-db > ~/macos-ca-bundle.pem
export NODE_EXTRA_CA_CERTS=~/macos-ca-bundle.pem   # добавьте в ~/.zshrc, чтобы не повторять
npm install
```

Собранному приложению npm не нужен: папку `dist/` (результат `npm run build`)
можно раздать любым статическим сервером, например `python3 -m http.server 8080`
внутри неё, и открыть `http://localhost:8080`.

### iPhone и другие компьютеры в локальной сети

По `http://<адрес-мака>:8080` устройства в той же Wi-Fi сети откроют
приложение, но камеру браузер даст только по HTTPS — значит, по HTTP они
могут быть лишь отправителями. Для приёма запустите HTTPS-сервер (нужны
только встроенные `python3` и `openssl`):

```bash
python3 scripts/serve-https.py dist     # или: python3 serve-https.py в папке готовой сборки
```

Скрипт создаёт в `~/.qr-air-transfer` локальный удостоверяющий центр
(ограниченный именами `*.local` и частными IP — для настоящих сайтов он
недействителен), выпускает сертификат для имени `<имя-мака>.local` и печатает
адреса. На iPhone один раз:

1. Safari → `https://<имя-мака>.local:8443/qr-air-ca.crt` (предупреждение о
   сертификате → «Подробнее» → «посетить этот веб-сайт») → «Разрешить» загрузку
   профиля. Либо перешлите файл `~/.qr-air-transfer/qr-air-ca.pem` через AirDrop.
2. Настройки → «Профиль загружен» → «Установить».
3. Настройки → Основные → Об этом устройстве → Доверие сертификатам → включить
   «QR Air Transfer local CA».

После этого `https://<имя-мака>.local:8443` открывается без предупреждений,
камера работает, приложение кэшируется для офлайна. Удалить профиль:
Настройки → Основные → VPN и управление устройством.

На другом Mac проще всего запустить свою копию (`python3 -m http.server 8080`
в папке сборки) и открыть `http://localhost:8080` — на localhost камера
разрешена без сертификатов.

Чтобы пользоваться совсем без сети, откройте приложение один раз (сервис-воркер
закэширует всё, включая WebAssembly-распознаватель) и добавьте его на главный
экран.

## Как это устроено

```
файлы ─► архив ─────► fountain-код ─► кадр (заголовок + отбеливание) ─► QR ─► экран
         (имена, CRC,  (систематический                                        │
          сжатие CM /   + плотные XOR-                                         ▼
          deflate)      комбинации)                                         камера
                                                                               │
файлы ◄─ проверка CRC ◄─ метод Гаусса над GF(2) ◄─ разбор кадра ◄─ ZXing (WASM) ◄┘
         + распаковка    (воркер)                                  (1–4 воркера)
```

| Модуль | Назначение |
|---|---|
| `src/core/qr/` | Собственный QR-энкодер: шаблон версии строится один раз, кадр кодируется за ~1 мс (v40) |
| `src/core/fountain/` | Бесскоростной код: поколения ≤ 1024 блоков, систематическая часть + случайные линейные комбинации, инкрементальный ML-декодер |
| `src/core/protocol.ts` | Формат кадра и «отбеливание» нагрузки |
| `src/core/cm.ts` | Компрессор смешивания контекстов (PAQ-класс), только целочисленная арифметика |
| `src/core/container.ts` | Архив из нескольких файлов, CRC-32, выбор метода сжатия по полному времени передачи |
| `src/core/zip.ts` | ZIP для «сохранить всё» |
| `src/core/transfer.ts` | Состояния отправителя/получателя, защита от чужих и ошибочных кодов |
| `src/core/resume-store.ts`, `resume-idb.ts` | Продолжение после перезагрузки: журнал кадров в IndexedDB, позиция отправителя |
| `src/core/limits.ts` | Модель канала «экран → камера» |
| `src/workers/` | Генерация кадров, распознавание ZXing, декодирование fountain-кода, упаковка/распаковка — вне основного потока |
| `src/ui/` | Интерфейс (без фреймворков) |

### Формат кадра (15 байт заголовка)

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | `0x51` — протокол v1 |
| 1 | 4 | ID передачи (хеш содержимого и размера блока) |
| 5 | 4 | Длина потока (u32 → предел 4 ГиБ) |
| 9 | 2 | Размер блока |
| 11 | 4 | Номер символа |
| 15 | B | Символ fountain-кода, XOR с псевдослучайной гаммой |

Получатель начинает приём только после двух согласованных кадров одной
передачи (один ошибочно прочитанный код не заставит выделить гигабайты) и
игнорирует посторонние QR-коды.

### Почему так быстро

* **Фиксированная маска + отбеливание.** Стандартный перебор 8 масок QR стоит
  ~22 мс на v40; отбеленные данные всегда «шумоподобны», поэтому маска
  фиксирована и кадр кодируется в ~20 раз быстрее.
* **Fountain-код с ML-декодированием.** Систематический LT при 10 % потерь
  требует на 30–44 % больше кадров; плотные комбинации + метод Гаусса — лишь
  ≈ 2 кадра сверх минимума при любой доле потерь.
* **Конвейер на воркерах.** Кадры генерируются заранее, распознавание идёт
  параллельно в нескольких потоках, решение системы — в отдельном воркере.
* **Целочисленное масштабирование.** Каждый модуль — целое число физических
  пикселей экрана: без муара и размытия.
* **Сжатие по полному времени.** Смешивание контекстов (класс PAQ) уменьшает
  тексты, таблицы и код в 3–10 раз; метод выбирается так, чтобы сжатие +
  передача + распаковка были минимальны (подробности — docs/THEORY.md, раздел 7).
* **Слежение за каждым кодом.** Найдя коды, приёмник анализирует лишь
  область вокруг каждого, уменьшенную до ~3,5 пикселя на модуль, каждую в
  своём потоке, — успевает обработать каждый кадр камеры 60 к/с. С двумя
  кодами на экране это дало 40–53 кода/с против 31,5 при общей области.
* **Без биений.** Частота смены кодов выбирается так, чтобы на каждый код
  приходилось ≥ 3 кадра камеры 60 к/с: иначе часы камеры и экрана периодически
  «синхронизируются» на неудачной фазе, и приём замирает.

## Тесты

* `tests/qr-encoder.test.ts` — все 40 версий × 4 уровня коррекции и все 8 масок
  декодируются эталонным ZXing.
* `tests/cm.test.ts`, `tests/container.test.ts` — сжатие без потерь на краевых
  случаях, замороженный формат, выбор метода по времени, архивы из нескольких
  файлов, ZIP (проверяется Python `zipfile`), чтение старого формата.
* `tests/fountain.test.ts` — восстановление при 0–60 % потерь, подключении с
  середины потока, нескольких поколениях.
* `tests/pipeline.test.ts` — файл → QR → «камера» (поворот, дробный масштаб,
  размытие, шум, 25 % пропущенных кадров) → файл.
* `tests/roi.test.ts`, `tests/tracks.test.ts`, `tests/phase-lock.test.ts`,
  `tests/limits.test.ts` — области слежения, стабильность размеров, раздельное
  слежение за несколькими кодами, модель биений камеры и экрана, авторежим.
* `e2e/app.spec.ts` — в реальном Chromium: скриншоты экрана отправителя
  (2 файла) собираются в исходные файлы; получатель с фейковой камерой 60 к/с
  принимает архив из 3 файлов со сжатием CM и отдаёт ZIP; авторежим выбирает
  2 кода друг над другом на широком экране и 1 на телефоне; камера
  включается сама, если доступ разрешён.
* `e2e/multi.spec.ts` — два кода друг над другом, камера держится
  вертикально: приёмник читает практически все коды клипа (51–53 уникальных
  кода/с, порог теста 45; одна общая область давала 31,5) и побайтная
  проверка файла. Время меряется внутри страницы: ожидание Playwright
  проверяет экран раз в 0,1–1 с и давало скачки на 0,5–1 с.
* `tests/tracks-decode.test.ts` — обрезка вокруг кода не захватывает
  соседний код (12 модулей до соседа) и читается при 3–4 пикселях на модуль
  с размытием и шумом, камера вертикально и горизонтально.
* `tests/resume.test.ts`, `e2e/resume.spec.ts` — журнал кадров (пакетная
  запись, восстановление, очистка, сбои хранилища), детерминированный ID;
  в Chromium: перезагрузка посреди приёма → прогресс на месте → приём
  завершается; «Начать заново»; отправитель продолжает с места остановки.
